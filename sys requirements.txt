# Software Requirements Specification — Functional & Non-Functional Requirements

## 1. System Overview

The proposed system is a **mobile-first, modular SME Business Management Platform** designed for small and medium-sized businesses in Malawi that cannot afford or effectively use traditional ERP systems.

The platform aims to:

* Reduce operating costs
* Increase revenue
* Reduce human errors
* Save time
* Improve business decision-making
* Improve record keeping
* Help informal businesses gradually formalize their operations
* Provide affordable access through a subscription model

The system will be developed using:

* **Backend:** Django
* **Frontend:** Django Templates + Bootstrap
* **Interactivity:** HTMX
* **Database:** PostgreSQL
* **Real-time:** Django Channels/WebSockets where required
* **Mobile:** Progressive Web App (PWA)
* **Payments:** PayChangu initially, with an abstraction layer for future gateways
* **Deployment:** Linux/VPS-based production environment

---

# 2. Core Modules

                 SME BUSINESS OS

       ┌───────────────┼────────────────┐

       │               │                │

The exact six can evolve, but **Accounts, Sales, Inventory, Finance, Customers and Reports** provide a strong initial foundation.

# 4. Non-Functional Requirements

Non-functional requirements describe **how well the system must operate**.

---

## NFR-01: Usability

The system shall provide a simple interface suitable for users with varying levels of digital literacy.

The interface shall:

* Use simple language
* Minimize unnecessary fields
* Minimize clicks/taps
* Use recognizable icons
* Provide clear error messages
* Provide guided workflows
* Avoid accounting jargon where unnecessary

Instead of:

> "Accounts Receivable"

the system might say:

> **"Customers who owe you"**

This is particularly important for informal businesses.

---

# NFR-02: Mobile-First Design

The system shall be designed primarily for smartphones.

The UI shall:

* Work on small screens
* Support touch interaction
* Use large buttons
* Minimize typing
* Support camera access
* Support barcode scanning
* Support PWA installation

Desktop screens shall be an extension of the mobile experience rather than the other way around.

---

# NFR-03: Performance

The system should provide fast responses under normal operating conditions.

Target:

* Normal page response: **<2 seconds**
* Common HTMX operations: **<1 second where practical**
* Dashboard loading: **<3 seconds**
* Barcode lookup: **near-instant after local/cache lookup**

Heavy reports should be generated asynchronously where necessary.

---

# NFR-04: Availability

The production system should target:

> **99.5%+ monthly availability**

excluding scheduled maintenance.

The system should have:

* Monitoring
* Error logging
* Health checks
* Automated backups
* Recovery procedures

---

# NFR-05: Scalability

The system shall support growth from:

```text
10 businesses
     ↓
1,000 businesses
     ↓
10,000+ businesses
```

The architecture should allow:

* Database scaling
* Horizontal application scaling
* Background workers
* Redis caching
* CDN/static-file optimization
* Separate reporting workloads

---

# NFR-06: Security

The system shall implement:

* HTTPS
* Secure password hashing
* CSRF protection
* XSS protection
* SQL injection protection
* Secure sessions
* Rate limiting
* Authentication
* Role-based authorization
* Object-level authorization
* Secure file uploads
* Audit logging

Django's built-in security mechanisms should be used wherever possible.

---

# NFR-07: Tenant Isolation

Tenant isolation shall be enforced at the application/data-access layer.

Every business transaction should be scoped to:

```text
request.user.organization
```

The system must prevent users from manipulating IDs to access another organization's records.

For example:

```text
/sales/105/
```

must not allow an employee from Organization A to view Sale #105 belonging to Organization B.

---

# NFR-08: Reliability

The system shall preserve transaction consistency.

For example, completing a sale should not produce:

```text
Sale = successful
Inventory = unchanged
Payment = recorded
```

Instead, related operations should use appropriate database transactions.

Conceptually:

```text
BEGIN TRANSACTION

Create Sale
Create SaleItems
Create Payment
Create StockMovements

COMMIT
```

If something fails:

```text
ROLLBACK
```

---

# NFR-09: Data Integrity

The system shall enforce:

* Foreign-key constraints
* Unique constraints
* Validation
* Decimal financial calculations
* Transaction integrity
* Referential integrity

Financial values should use:

```python
Decimal
```

rather than floating-point numbers.

---

# NFR-10: Backup & Recovery

The database shall be backed up automatically.

A production strategy could include:

* Daily full backups
* More frequent incremental/WAL backups
* Off-server backup storage
* Backup encryption
* Backup verification
* Defined recovery procedures

The target should be something like:

**RPO:** ≤ 24 hours initially
**RTO:** ≤ 4 hours initially

These targets can become stricter as the platform grows.

```text

```

## The key distinction

Your **functional requirements** define the product:

> *"The system shall allow a business owner to record a sale."*

Your **non-functional requirements** define the quality:

> *"The sale shall be recorded securely, accurately, quickly, within the correct organization, and without creating inconsistent inventory or payment records."*

For this particular project, I would put **multi-tenancy, offline capability, low-bandwidth performance, payment reliability, security, and simple UX** much higher than they would appear in a conventional ERP SRS. Those are what make it genuinely suitable for the informal and semi-formal SME market you're targeting.
